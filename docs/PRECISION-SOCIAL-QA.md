## 실패 단계를 분리한 결과

- 이전16문항의 우려·농담·확인 누락3건은 올바른 후보가 있고 입력도5200토큰 한도 미만이었다. 모델은 `bot continue`를 선택한 뒤 `other no`로 끝냈다. 후보 생성이나 GPU 만료가 아니라 **발화행위/답변 기대의 복합 출력** 실패였다.
- 새 사용자가 봇 답변의 내용을 재질문할 때, 최초 사람 질문의 topic만 검색하여 실제 봇 출처를 놓치는 경로를 확인했다. 후보 검색을 실제 보존한 답변까지 넓히되, 최종 연결은 한 번의 관계 분류와 검증을 거친다.

- 남은 일부 실패는 후보/출처가 있어도 모델이 수신 확인으로 오인하거나 잘못된 흐름을 선택하는 경우다. 원인별 private 분석에는 후보 수·모델 계획·검증 사유·후속 단계 코드를 구분한다. 최종 SILENCE를 모두 청자 오판으로 합산하지 않는다.

## 채택한 실행 계약

`response_plans.py`는 **실제 화자가 확인된 peer인 후보 인덱스만** reply/receipt/end 계획으로 제공한다. 다른 사람·제외·방송·단순 전달·불확실·새 요청을 별도로 표현한다. 독립적인 yes/no와 발화행위의 직교 조합을 줄였지만, 명확한 타인 호칭·reply·미해결 사람 간 대화·범위·최신 상태·송신 검증은 그대로 적용한다. 모델은 User ID나 Discord API 권한을 만들 수 없다.

의미 판정은 기본적으로 한 번이다. 실제 출처를 새로 찾는 일부 직접 호출에는 유용한 관계 판정이 추가될 수 있으며 이를 호출 수에서 숨기지 않는다. 시간과 활동 수준을 의미 입력에 넣지 않는다. 기존4활동×간격·프로필 회귀,32세션 상한·원본 reply·중복 방지 검사를 유지한다.

진단에는 response_expected·decision_plan·candidate_count·peer_candidate_count·context_omitted·pending_human_exchange를 기록한다. 모델의 비공개 추론 원문은 아니다. QA의 입력/판정 원문은 `local_data`에만 저장한다.

## UI 검증 경계에서 발견한 검사 실수

초기199/209 디스패치 실행은 서버 목록 새로고침의 HTTP 경계를 빠뜨렸다. **합성 가짜 토큰으로 인증 요청2건이 나가 LoginFailure로 거절됐다.** 운영 토큰 사용·실계정 로그인·Gateway·서버 메시지 송신은 없었지만 사용자의 무접속 지시를 충족한 실행이 아니므로 폐기했다. 실패 기록을 보존했다.

이후 실제 discord.py 파서에는 합성 HTTP 응답만 제공하고 aiohttp 하위 요청은 강제 차단했다. Controller 오류도 실패로 판정하도록 수정했다. 최종 UI 결과와 미실행/경계 mock은 [UI 동작 QA](UI-ACTION-QA.md)를 따른다. 이 실수를 실제 Discord 검증 성공으로 사용하지 않는다.

추가 보호 검사의 초기 버전은 운영 모듈을 먼저 로딩한다는 사전조건이 빠져 자체 오프라인 검증 창을 잠시 표시했다. 해당 unittest 자식 프로세스를 명령·부모 PID로 확인해 그 프로세스만 종료했다. 마우스/키보드 자동 입력이나 사용자 앱 종료는 하지 않았다. 이 실행도 성공 근거에서 제외하고 사전조건 및 Tk 생성 자체를 차단하는 시험 guard를 추가했다.
