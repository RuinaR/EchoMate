| 실제 봇 답변·원본 | 실제 메시지 ID·작성자·bot 표시·reply 출처가 frames에 있다. 모델의 frame 인덱스는 런타임의 snapshot/version과 대조하며 추론 User ID로 접근 권한을 만들지 않는다. |
| 전달·현재 질문 | 보고된 발언과 바깥 질문은 현재 원문에 모두 있었고 기존 정책도 둘을 구분하도록 지시했다. 정정·전달문 질문의 직전 실패는 짧은 입력·온전한 실제 답변에서도 발생했다. 이 사례를 문맥 누락 탓으로 돌리지 않는다. 별도의 의미 절 분리기는 구현하지 않았으며 해당 모델 판단 한계는 남는다. |
| 응답 계획·검증 | 정정의 receipt, 전달문 바깥 질문의 human, 독립 요청의 continue가 먼저 선택됐다. 이후 검증이 올바른 판단을 거부한 문제나 큐·송신 오류와 구분한다. 직접 호출의 불확실한 연결은 원본 요청을 독립 응답으로 보존한다. |
| 여러 흐름 | 같은 화자·주제·시각은 연결 확정 근거가 아니다. 시간·활동 값으로 청자를 바꾸거나 불특정 발언에 응답 권한을 추가하지 않았다. |

## 유지한 수정 — 실제 출처를 잃지 않는 제한된 창

`social_evidence.py`는 최신 실제 봇 답변과 그 원본 요청, 실제 reply가 지목한 메시지와 부모를 먼저 보존하고 남는 자리를 최근 실제 발언으로 채운다. 6개 frame 창·4개 직접 연결 창을 유지하며 없는/만료된 부모나 발언을 만들지 않는다.

이전에는 봇 답변이 RAM에 있어도 보충 발언이 많이 쌓이면 마지막6개/4개 슬라이스가 그 답변을 제외했다. 이후 토큰 예산 축약에서도 첫 발언을 무조건 지워 출처를 다시 잃을 수 있었다. 이제 예산 축약은 보호된 출처 외의 발언만 제거하고, 모두 보호된 상태에서도 예산을 넘으면 불확실한 입력으로 실패 처리한다. 480자 본문이 잘린 경우 `text_clipped`로 표시한다. 짧은 입력의 기존 원문·순서·필드는 유지한다.

또한 frame의 마지막 수신자는 임의로 선택한 sibling의 상태값 대신 **마지막 실제 봇 reply의 보존된 부모 작성자**로 계산한다. 병합된 이력과 sibling 상태가 다를 때의 합성 재현을 추가했다. 부모가 없으면 수신자를 지어내지 않는다. 이는 짧은 정정/전달문 의미 실패와 별개의 근거 불일치 수정이다.

## 비교하고 기각한 대안

기존 프롬프트·라벨·출력 제한을 유지한 채 두 후보 beam 탐색을 시험했다. 이전의 행동 설명/단일 기호 후보를 이름만 바꾼 실험이 아니다. 전체 입력 패킷36개가 대조군과 동일함을 확인했다. 단일 GPU 큐·기본 모델·안전 기준은 그대로였으며 실험은 로컬 검증 도구에서만 적용했다.

| 재사용 개발 36문항 | 기존 탐욕 선택 | 두 후보 탐색 |
|---|---:|---:|
| 오류 없는 통과 | 33/36 | 28/36 |
| 기존 행동 일치 집계 (오류 미분리) | 33/36 | 31/36 |
| 오개입 / 누락 / 연결 오류 | 0 / 2 / 1 | 0 / 2 / 3 |
| 실제 Worker 호출 | 28 완료 | 21 완료 + 7 실패 |
| 수신→판단/모의 응답 p50 / p95 | 0.7650 / 1.3397초 | 1.0470 / 2.0200초 |

7건은 단순 모델 오답이 아니라 백엔드 ValueError였다. 한 건을 추가 추적해 Transformers의 prefix callback에서 `Invalid constrained output prefix`가 발생함을 확인했다. 유한 문법과 선택한 beam 경로가 호환되지 않았다. 실패한 호출이 완료 metrics 목록에 없더라도 Trace의 Worker 실패 기록에는 있으므로 **호출이28→21로 감소했다고 주장하지 않는다**. 검증을 느슨하게 하거나 프롬프트를 반복 조정하지 않고 기각했다. 개발 조건부터 악화돼 독립 평가에 이 후보를 확장하지 않았다. 생산 디코딩은 변경하지 않았다.

이 과정에서 평가 도구가 분류 예외로 침묵한 음성 문항을 정답으로 세거나, 연결 판정 예외 후 안전한 독립 응답을 모델의 연결 성공으로 셀 수 있음을 발견했다. `behavior_ok`와 `inference_ok`를 분리하고 둘 다 맞아야 전체 통과하도록 수정했다. 실패·취소된 Worker도 호출에 포함하고, 완료 계측은 현재 요청의 Trace에서 가져온다. 전역 metrics의 최근200개 보존 한도나 이전 문항의 피크가 현재 문항 집계를 오염시키지 않게 했다. 저장된 원본은 수정하지 않고 오프라인 엄격 재집계 파일을 별도로 남겼다. 후보의31건 중3건은 예외가 있었으므로 엄격 통과는28건이다. GPU를 재실행한 수치가 아니며 실패를 지운 점수도 아니다.

추가로 한국어 봇 호격이 연결 검색어에 남는다는 가설을 감사했으나, 실제 `terms()`가 앞 두 글자로 정규화하므로 해당 호칭은 기존에도 제외됐다. 제한된5사례 비교는 양쪽5/5·호출3회로 차이가 없었다. 가설과 불필요한 수정은 철회했다. 기존 요청 보존과 실제 출처 연결의 유지 확인으로만 기록하며 품질/속도 개선으로 세지 않는다.

## 독립 평가와 실제 GPU 검증

네 상황·여러 화자·두 독립 흐름을 포함한32문항을 결과 확인 전 고정했다. 두 후보 실험은 이 세트로 튜닝하지 않았다. 안정적인 기존 선택의 기준선과 최종 입력 보존 코드가 모두 **29/32**, 오개입0·누락3·연결0이었다. 정정·우려/농담·전달문 바깥 질문에서 각각1건 누락했다. 일반 의미 품질 향상을 확인한 결과가 아니다. 이후 이 세트는 회귀 자료로만 사용한다.

최종32건의 실제 GPU Worker 호출은28회, 큐 대기0, 판단/모의 텍스트 경로 p50/p95 **0.7500/1.3750초**였다. 실제 텍스트 생성 시간이 아니다. 기준선은 다른 모델 로딩 세션이므로 두 세션 간 차이를 속도 개선의 인과 근거로 사용하지 않는다. 최종 GPU manifest의 전체 소스 해시와 현재 소스가 일치함을 확인했다.

- **실제 GPU + 모의 그룹 상태 PASS:** 세 번의 종료 판단에서 활동 흐름 수1→1→0, 수신자별 engaged `[false,true]`→`[false,true]`→`[false,false]`. 다른 수신자의 진행 작업은 취소되지 않았다. 단일 Worker 호출3회. 실제 Discord 그룹 시험이나 사람의 자연스러움 판정은 아니다.
- **실제 생성→모의 전송 2/2:** 짧은 직접 호출2.890초/17토큰, 우려를 담은 후속6.250초/46토큰. 후속은 의미 판단1회+생성1회, 직접 호출은 생성1회로 총 Worker3회다. 혼합 p50/p95 4.570/6.082초는 2건의 보간값일 뿐 운영 지연 통계가 아니다. 실제 생성 TTFT는0.594/0.610초, 생성속도6.078/8.710tokens/s, 큐0·재생성0이었다. 이전의 다른 출력 길이와 속도 향상으로 비교하지 않는다.
- 정상 종료 세션은 allocated1024bytes·reserved2MiB, 종료 후 Worker0. 진단용 예외 재현 세션에서는 검증 도구의 bound generate 참조가 남아 종료 계측 때 가중치가 유지됐다. 해당 수치를 정상 unload 실패나 장시간 누수 인증으로 사용하지 않는다. 그 프로세스 종료 뒤 집계 VRAM도 모델 없는 수준으로 복귀했다. 로더·GPU 안전 기준·시스템 설정은 바꾸지 않았다.
- 최초 그룹 검증 도구는 비동기 완료 전 조회로 IndexError가 났고, CPU 점검에서는 legacy chooser가 같은 흐름을 재사용한 fixture 문제도 확인했다. 두 결과는 검증에서 제외·보존했다. 별도 실제 흐름 구성과 완료 대기를 CPU에서 확인한 뒤 수정된 GPU 검증만 PASS로 기록했다.

## 회귀·보존·릴리즈

최종 전체 회귀 **602개 OK74.830초**. 중간598개 OK76.385초 후 QA 실패 집계 회귀4개를 추가해 전체를 마감했다. `PYTHONPATH=src;tests;tools`에서 `.venv-gemma4/Scripts/python.exe -m unittest discover -s tests -q`로 확인했다. 실제 종료·pending 보존·범위·동의·기억·알림·검색·UI 등 기존 검사와 함께 출처 창/예산 축약/reply 수신자 회귀를 확인했다. 운영 설정·bootstrap·관계/기억 DB·송신 ledger의 전후 SHA-256 **4/4 일치**도 확인했다. 모델·LoRA·설정·운영 DB를 변경·초기화하지 않으며 비공개 산출물은 Git 대상에서 제외한다.
