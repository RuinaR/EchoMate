## 2026-10-19 — 의미 중심 참여·명확한 호칭·기분 표현 개선

이전 병렬 구조를 보존하며 의미 중심 라우팅을 추가했다. 명확한 이름 호출/실제 멘션/reply는 모델의 참여 veto로 사라지지 않는다. 일반 후속은 문장부호·고정 요청 목록을 운영 빠른 경로로 쓰지 않고 공통 기본 모델의 발화행위/대상/연결/반응 가치를 판단한다.

새 참가자의 단독 확정 호출은 유일한 진행 대화에 합류할 수 있다. 다른 합류 후보는 의미 승인 후 실제 발언만 공유한다. 현재 봇 행동에 대한 그룹 평가도 기존 지속이며 신규 자율 참여 확률을 다시 적용하지 않는다. 별개 질문과 원본 답장 대상/FIFO는 보존한다. 생성 중 이름 호출은 연결 판정 때문에 호출 자체가 없어지지 않는다.

작성자 FIFO 뒤 최신 공유 잠금을 선택하고, stale 후보를 합치지 않는다. 합류 기억은 확정된 flow ID로 지연 처리하며 옆 대화가 활성 수를 계속 부풀리지 않는다. 직접 호출/기존 지속과 신규 자율 진입의 쿨타임·부하 보정 구분은 유지한다.

## 최신 참여 정책

진행 중인 대화가 있다는 이유로 **다른 채널·스레드의 신규 자율 참여를 전역 차단하지 않는다.** 앞서 요청된 전역 차단은 이후 명시 지시로 대체됐다.

- 직접 멘션·이름 호출 후보, 실제 봇 답장, 근거가 있는 기존 대화 지속은 신규 자율 참여 확률/쿨타임과 구분한다. 이름 후보는 의미적 대상 검증을 통과해야 한다.
- 같은 채널에서 기존 대화가 진행 중이면 무관한 새 흐름에 자율 진입하지 않는다. 다른 범위는 활성 수·GPU 부하를 고려해 보수적으로 판단한다.
- 자율 진입 확률은 기존 활동 수준 확률을 `1 + 0.5×활성 대화 수 + 0.5×GPU 대기·실행 수`로 나눈다. GPU 작업이 용량의75% 이상이면 새 자율 진입을 보류한다. 기존 대화/직접 요청을 이 확률로 버리지 않는다.
- 범위별 마지막 활성 대화가 끝나면 그 범위의 자율 진입 쿨타임을 새로 시작한다. 다른 채널의 종료로 전체 쿨타임을 다시 시작하지 않는다.
- 활성 수는 저장된 세션 수가 아니다. 참여 승인/실제 봇 발언/미완료 요청, 마지막 실제 상호작용, 명시적·의미적 종료를 사용한다. 상호작용 없이 `min(300초, 문맥 보관 설정)`이 지나면 부하용 활성 집계에서 제외한다. 이는 문맥 삭제나 대화가 실제로 끝났다는 확정이 아니다. 명확한 후속 질문은 이후에도 지속 경로로 복귀할 수 있다.

## 상태와 라우팅

`sessions.Conversations`는 guild/channel/thread 범위, RAM conversation ID, 실제 참여자 ID·원본/답장 ID, 최근 주제, 마지막 봇 메시지와 참여/종료 상태를 유지한다. 첫 흐름의 내부 키는 기존 channel 키와 호환하고, 같은 채널의 추가 흐름은 별도 키로 관리한다. 정책과 Discord API에는 항상 실제 채널 ID를 전달한다.

다른 사용자의 명시적 요청은 별도 흐름이다. 실제 reply 관계로 같은 대화에 합류할 수 있고, 모호한 새 화자를 시간 인접만으로 합류시키지 않는다. 하나의 진행 중인 봇 대화에서 주제를 명확히 참조하는 다른 화자는 의미적 검증 후보로만 고려한다.

같은 사용자의 처리 중 요청에 명백한 조건·정정·보충이 붙으면 최신 실제 문맥으로 교체한다. 멘션/이름을 다시 붙인 보충도 호출 부분만 의도 판정에 사용하고 원문은 유지한다. 독립 질문·불확실한 보충은 별도 요청으로 보존한다. 보충/독립 구분은 보수적인 코드 규칙이며 모든 한국어를 이해하는 분류기가 아니다.

동일 작성자·같은 채널의 요청은 FIFO 잠금으로 생성·전송 순서를 보장한다. 명시적으로 공유한 대화도 별도 FIFO를 사용한다. 순서는 `작성자 FIFO → 공유 대화 FIFO → GPU admission → 채널 송신 잠금`이다. GPU를 점유한 채 대화 잠금을 기다리지 않는다. 다른 사용자의 독립 대화는 이 잠금에 묶이지 않는다.

공유 흐름의 대기 요청은 앞선 작업이 실제로 보낸 발언을 시작 시점에 합친다. 실제 메시지 ID로 중복 제거하고 시간순으로 보존하며, 응답 대상 원문을 별도 참조 자료로 명시한다. 생성한 요약이나 발언을 실제 과거 사실로 삽입하지 않는다. 관련 없는 conversation ID의 문맥은 합치지 않는다.

단일 상대 후속 경로 외에, 실제로 합류한 공유 대화의 기존 참여자가 직전 답변의 실질적 주제를 이어 묻는 경로를 추가했다. 다른 사람을 향한 답장/멘션·호격·인용·무관한 주제·불명확한 질문은 이 빠른 경로를 통과하지 않는다. 모호한 경우 의미 판단과 침묵을 유지한다.

## 원본 고정과 취소

- 모든 텍스트와 기본 스티커는 실제 원본에 Discord reply로 전송한다. 생성이 늦거나 다른 작업이 먼저 끝나도 최신 메시지로 답장 대상을 바꾸지 않는다.
- 보충 설명은 처음 요청 ID를 유지한다. 일반 reply는 멘션을 발생시키지 않으며 예약의 본인 명시 멘션과 구분한다.
- 송신 직전 실제 원본을 fetch하고 content hash를 비교한다. 보충 메시지도 따로 검사한다. Gateway 수정 이벤트를 놓쳐도 변경/삭제된 원본에 오래된 답을 보내지 않는다. 검사와 원격 전송 사이의 모든 경쟁을 원자적으로 막을 수 있다는 주장은 하지 않는다.
- ledger의 중복 키/nonce는 원본 ID에 고정한다. 전송 성공이 불명확한 예약 상태는 자동 재생하지 않는다.
- 메시지 수정/삭제·명시 취소는 관련 흐름에만 적용한다. 다른 참여자가 답장으로 타인의 요청을 취소할 수 없다. 설정/권한 변경은 전송 직전에도 검증한다.
- 완전 중복은 같은 범위·작성자의 최근10초 원문 해시로 억제한다. 코드·URL·인용의 대소문자나 공백을 정규화해 다른 요청을 지우지 않는다. 해시 목록은 최근65개/최대1000작성자 범위로 제한한다.
- 단순 연속 호출 횟수만으로 서로 다른 직접 질문을 버리지 않는다. 질문별 상태를 보존하며 자원 한도에서는 admission 대기/명시적 용량 거절을 사용한다. 무제한 보존을 약속하지 않는다.

## GPU 작업과 공정성

`scheduler.Request`: request ID, conversation ID, guild/channel/thread, requester/target message, type/priority, 생성 시각/deadline/context version, cancellation token/status. 이 식별 자료는 RAM 내부용이며 일반 진단에는 원문·ID를 기록하지 않는다.

`GPUScheduler` 앞단 큐와 기존 `ThreadPoolExecutor(max_workers=1)`를 재사용한다. 멘션/이름 후보 우선0, 지속1, 자율2, background3이다. 점수에서 대기5초마다1을 빼 오래된 낮은 우선순위가 새 작업에 영원히 밀리지 않게 한다. 실행 중 생성은 우선순위가 높다는 이유만으로 선점하지 않는다.

기본 GPU admission 한도12, 사용자당4/채널당8이며 내부 admission 대기32를 추가한다. 실제 Discord 논리 요청은 RAM 흐름 최대32에서 제한한다. 용량이 차도 직접 요청은 남은 deadline 동안 비동기로 자리를 기다린다. 기존 작업을 임의로 제거하거나 진행 중 대화를 용량 확보 목적으로 덮어쓰지 않는다. 포화/만료/취소는 숫자 상태로 남긴다. 런타임 요청 유효 기간은 수신부터180초이며 무제한 대기·정확히 한 번 발송은 보장하지 않는다.

취소는 실제 CUDA 작업이 중지될 때까지 단일 워커의 소유권을 유지한다. 반복 취소에도 아직 돌아가는 작업을 없는 것으로 계산하지 않는다. 모델 전환은 미송신 요청을 보존하고 정리·준비 후 재검사한다. 준비 실패는 이전 설정을 유지한다. GPU 기기 실패/자원 보호 중단은 전체 안전 정지, 일반 대화 오류3회는 해당 흐름만 일시 중단한다.

Gateway 일시 끊김은 문맥을 지우지 않고 미송신 요청을 RAM에 보류한다. 재연결/모델 전환이 겹쳐도 허용 범위·deadline·ledger를 재검사한다. API 전송을 이미 예약한 불명확한 요청은 재전송하지 않는다. 앱 완전 종료 후 미완료 텍스트 요청은 재생하지 않는다. 예약 알림은 별도 SQLite 복구 정책을 따른다.

기억 추출/관계/발췌는 기존 CPU 경로이고 GPU 호출을 추가하지 않는다. 예약 scheduler도 GPU 큐나 대화 쿨타임을 기다리지 않는다. 이미지 분석은 확장하지 않았고 기본 비활성 상태를 유지한다.

## 기억·동의·마이그레이션

SQLite schema3: schema1 자료를 초기화하지 않고 memory_flows와 subject_consents를 트랜잭션 안에서 추가한다. 출처/화자/시간/삭제·만료 규칙을 보존한다. foreign key로 기억 삭제 시 흐름 참조도 삭제한다. 신규 버전을 구버전 코드로 읽지 못할 때 DB를 초기화하면 안 된다.

약속·상태·목표 같은 작업 기억은 conversation ID로 제한한다. 본인 취향/명시 기억은 사용자 사실로 유지하되 관련성·서버·사용자·출처 채널을 검사한다. 본인이 명시적으로 자신의 약속/기억을 조회하는 경우에만 보관 자료 범위까지 조회한다. 다른 사용자의 기억은 공유 대화에 합류해도 조회하지 않는다.

소유자가 자동 저장을 켰다는 이유로 다른 구성원이 동의한 것으로 간주하지 않는다. 다른 구성원은 `/내기억 → 본인 자동 기억·관계 저장 허용`을 직접 선택해야 자동 추출/관계 갱신 대상이 된다. 전체 삭제로 철회할 수 있다. 소유자 자신의 데이터 사용 요청과 개별 명시 기억/알림 요청은 구분한다. 기존 자료는 삭제하지 않으며 과거 자료의 사용 허가를 자동으로 인증하지 않는다. 법적·Discord 정책상 사용 가능성은 자동 검사만으로 확정하지 않는다.

## 관리 앱과 진단

진행 화면은 실제 활성 대화 수, 전체 논리 요청 수, GPU 실행/대기·최장 대기·최근 완료/취소/실패를 구별한다. 작성자 FIFO 대기는 ‘앞선 질문을 처리하는 중’으로 표시한다. 다중 대화일 때만 추가 큐 정보를 보여 주고 메시지 원문/사용자 ID는 노출하지 않는다. 개인정보 제외 진단 내보내기에 큐 집계를 포함한다.

100/125/150%에 해당하는 Tk scale4/3·5/3·2에서 숨긴 창 레이아웃을 검사한다. 이는 실제 사용자 화면 조작/스크롤·포커스 관찰과 다르다. 사용자가 컴퓨터 조작을 끄도록 요청해 화면/마우스/키보드 자동 조작은 하지 않는다.

## GPU 결과

원본은 `local_data/parallel-qa-20261019/`에만 보관한다. GPU 스냅샷은 단계별 코드이며 최종 소스와 차이를 기록한다. 실험 중 모델 가중치·학습 자료·서명 설정은 변경하지 않았다.

초기 동일 단일 질문(숫자 답변) 비교는 워밍업1쌍 제외, 순서 교대, 모드당5쌍이다. 같은 현재 GPU backend에 기준 eaf1d1e/변경 runtime을 사용했고 프롬프트 해시/답변은 각5/5 일치했다.

5쌍의 짧은 합성 질문이다. 작은 차이를 통계적 속도 개선으로 주장하지 않는다. 초기 단계 측정 후 추가된 FIFO·동의·공유 문맥 가드는 별도 기능/최종 소스 GPU 검사로 검증했다. 이 수치를 모든 최신 경로의 속도로 일반화하지 않는다.

실제 생성 중 두 번째 사용자 요청을 넣은 gpu-2는 세 모드 각각3회 중첩을 확인했다. 기준은 각각3/6응답(3누락), 변경은6/6(0누락), 잘못된 대상0이었다. 변경은 더 많은 답을 실제 생성하므로 총 소요시간을 기준과 동일 작업 속도 비교로 쓰지 않는다.

| 모드 | 중첩 응답 p50/p95 초(n=6) | GPU 큐 p95 초(n=7호출) | 최대 allocated/reserved MiB |

생성·판단 호출을 포함한 worker TTFT p50은0.391/0.406/0.406초였다. 실제 Discord 네트워크 지연을 포함하지 않는다. 긴 생성은 비선점 워커의 뒤 요청을 지연시키므로 무조건 즉시 응답을 보장하지 않는다.

같은 작성자의 gpu-bursts-2: 세 모드×(1/2/5초 독립 질문, GPU 대기 중, 이름을 붙인 보충, 완전 중복)=18/18 통과. 독립 질문 생성/답장 대상 순서 보존, 보충은 최초 대상, 중복 전송0. 모든 두 번째 호출 시 실제 GPU 작업이 있었다. 의도한 보충 교체 취소는 모드당1회다. 장문 blocker를 포함한 응답 p95는25.491/27.619/30.631초였으며 짧은 질문 단독과 비교하지 않는다.

5/10/20/50턴의 합성 실제 발언을 넣은 회상은 세 모드 모두 지정 사실을 포함했다(12/12). 50번의 실제 상호 생성이나 자연스러운 장기 대화 전체를 검증한 결과는 아니다.

공유 대화 gpu-group-1에서 기본의 후속1건 누락을 발견했고 개인/성인 모드는 사실 갱신을 유지했다. 근거 있는 공유 후속 경로를 보강한 뒤 다른 이름/값을 사용한 gpu-group-2에서 세 모드 모두4개 대상과 변경 사실을 유지했다. 이는 작은 합성 회귀이며 독립된 사람 블라인드 품질 평가가 아니다.

실제 GPU lifecycle 시험: 생성 중 base→persona 전환에 대기 원본2개 보존, 준비 실패 주입 후 선택 유지와 실제 GPU 재응답, GPU 작업 중 SQLite 알림1회 발송 성공. 발송은 모의 transport 약0.015초이며 실제 Discord API 지연이 아니다. 세부 결과는 해당 summary.json을 따른다.

초기 테스트의 import 순서 오류, Windows 타이머 조기 기상으로 인한 발언 간격 누락, 단일 채널 취소/일반 오류 전역 전파, 재연결 문맥 소실, 송신 직전 편집 미검출도 수정했고 실패 로그를 보존했다. 자동 평가 숫자로 모델 최종 선정을 하지 않는다.
