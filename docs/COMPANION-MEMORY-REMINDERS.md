# 공통 대화·관계·기억·예약 알림

2026-10-19 구현. 기본 Gemma 4, 개인 말투 LoRA, 성인 유머 정책 모드에 같은 애플리케이션 계층을 적용한다. 성인 유머 선택지는 여전히 기존 기본 가중치+정책 대안이다. 새 학습이나 GGUF 실사용 승격은 없다.

## 범위와 권한

- 소유자 ID와 기존 HMAC 설정 검증을 유지한다. 서버 이름/사용자 표시 이름은 식별자로 사용하지 않는다.
- 별칭·접미사 생략 호출은 응답 후보일 뿐이다. 허용 서버/채널/스레드, 대상 구분, 안전/취소 검사는 그대로 적용한다.
- 본인 기억·알림 명령은 본인의 레코드만 조회·삭제한다. 소유자 전체 관리는 Windows 앱에서 수행한다.
- 자동 기억은 기본 OFF다. 관계 변화는 숫자 메타데이터이며 권한·안전·활동 범위를 바꾸지 않는다. 원문 전체를 장기 기억으로 복사하지 않는다.
- 비공개 SQLite `local_data/bot/companion.sqlite3`와 QA 산출물을 Git에 추가하지 않는다. 진단 내보내기에 기억/알림 본문은 포함하지 않는다.

## 구현 경계

`context.py`: 최근 실제 발언과 원본 ID가 연결된 과거 발언 발췌를 제한된 예산 안에 구성한다. 생성한 가상 요약을 과거 사실로 저장하지 않는다. RAM은 채널당 최대100발언/전체32채널과 시간 보조 정리로 제한한다. 원본 답장·화자·수정/삭제 버전을 유지한다. 재시작 시 Discord 과거 기록을 자동 수집하지 않으며 RAM은 초기화된다.

`routing.py`: 실제 봇 답장과 같은 상대의 명백한 후속 질문은 신규 진입 확률을 다시 적용하지 않는다. 다른 화자/대상, 종료, 인용, 옆 대화가 끼면 의미 판단을 거친다. 고정 메시지 수나 타이머만으로 대화 종료를 확정하지 않는다. 모호한 다중 화자 문맥의 누락은 남아 있다.

`companion_store.py`: 연결별 SQLite 트랜잭션/WAL/secure_delete, 짧은 잠금 대기와 오류 격리를 사용한다. 새 스키마나 손상 DB를 덮어쓰지 않는다. 오류는 형식/단계만 기록하고 기억 장애가 기본 대화를 전부 중단시키지 않도록 분리한다. 자동 백업을 만들지 않는다. SQLite 삭제는 저장장치·사용자 백업의 물리 삭제까지 보장하지 않는다.

`companion.py`, `temporal.py`: 추가 LLM 호출 없이 본인 요청과 시간을 보수적으로 해석한다. 일반적인 “모임 시간을 알려줘”를 알림 예약으로 오인하지 않는다. 실제 저장 commit 후에만 성공 응답한다. 모호한 문장에는 확인을 요청한다.

`memory_context.py`: 서버/사용자/출처 채널이 일치하는 활성 기억만 최대 예산 내 구조화한다. 최신 실제 발언이 우선이며 기억 내용은 신뢰할 수 없는 사용자 자료로 취급한다. 원래 관찰 시각과 계산한 절대 시각을 함께 제공해 “다음 주”를 현재 날짜로 다시 해석하지 않게 한다.

## 시간·만료·갱신

- 기준은 Discord 메시지의 시간과 서버 IANA 시간대(기본 Asia/Seoul)다. 저장은 UTC, UI는 서버 현지 시각이다. Windows용 tzdata를 고정했다.
- 숫자/한글 상대 시간, 복합 시간, 날짜·요일·다음 주·월말 등을 지원한다. 상대 시간은 UTC 경과 시간, 명시적 날짜는 현지 달력 기준이다. DST 중복/존재하지 않는 시각은 확정하지 않는다.
- “내일 3시”, “주말쯤”, 시간 없는 알림, 유효하지 않은 날짜/여러 시각은 추측하지 않는다. 자연어 전 범위를 처리하는 범용 파서는 아니다.
- 약속은 계산된 종료+유예, 잠깐의 상태는 짧은 TTL, 취향/명시 기억은 선택적 만료를 사용한다. 오래 확인하지 않은 목표는 확인 필요로 전환한다. 자동 추출은 자기 발언/명시 요청과 제한된 유형만 지원한다.
- 조회에서 만료 자료를 즉시 제외하고 시작/주기 정리로 삭제한다. 같은 약속의 명시적 변경·취소는 모호하지 않을 때만 반영한다.
- 삭제·원본 수정/삭제·사용 거부는 tombstone/cutoff로 대기 작업이 다시 저장하지 못하게 한다. 기억만 삭제할 때 관계나 예약은 함께 지우지 않는다. 전체 본인 자료 삭제는 명시적으로 구분한다.
- 관계는 중립50에서 대화/실제 봇 메시지 반응에만 천천히 변하며 10분 간격/하루 최대2 증가다. 반응 삭제는 원래 증가분을 한 번만 되돌리고 반복 추가로 점수를 얻지 못한다. 공격적인 문구 분류만으로 감점을 학습하지 않는다.

## 알림 발송과 실패

1. 본인이 요청한 허용 범위의 알림을 DB에 저장한다. 기본적으로 타인을 지정할 수 없다.
2. GPU 큐/발언 쿨다운과 독립된 1초 주기 스케줄러가 기한을 조회한다.
3. 최신 활성 설정, 범위, Discord 권한/대상 멤버/스레드 상태를 다시 확인한다. 전송 전 실패는 30초 후 다시 검사해 다른 예약을 막지 않는다.
4. 원자적으로 processing으로 선점하며 최신 수정 본문을 읽는다. processing 이후 편집/취소는 거부한다.
5. 요청자 한 명만 AllowedMentions로 허용하고 nonce를 사용한다. 역할/everyone/here 멘션과 임의 미디어는 보내지 않는다.
6. 성공 시 delivered, 송신 예외는 failed다. 성공 여부가 불명확한 HTTP 재전송이나 재시작 후 processing의 자동 재발송은 하지 않는다. 중복 방지가 우선이며 네트워크와 Discord 전체의 exactly-once는 보장하지 않는다.

재시작 시 기본15분 유예 안의 예약만 재검사하고 지난 예약은 expired 처리한다. 완료/실패/취소 본문은 지우고 상태 기록은7일 정리한다. 사용자당 활성10개/하루30개, 전체 활성1000개 제한이다. 스레드 이동·차단된 범위를 다른 채널로 우회하지 않는다.

## Windows 앱 사용

`EchoMate.vbs`로 실행한다. 기존 시작/모델/범위 화면을 유지하고 다음 영역을 추가했다.

- 사람과 관계: 서버→최근 관찰 사용자 선택, 친밀도/변화 이력, 수동 조정·초기화. 서버 이름 별칭/부분 호출/시간대도 관리한다.
- 기억 관리: 자동 저장 OFF/ON, 서버·사용자·종류·상태·만료/검색 필터, 출처/저장·확인 시각, 수동 추가·수정·만료·삭제·초기화.
- 예약 알림: 사용자·상태 필터, 예정/실패 우선 목록, 현지 시간·본문 수정/취소, 보존 기간 정리. 이미 발송 중인 자료는 수정하지 않는다.

설정은 즉시 반영하며 저장 실패를 표시한다. 목록 갱신은 UI 폴링마다 SQL을 실행하지 않고 별도 비동기 작업으로 수행한다. 목록은 유한하며 사람100명/사용자 기억100개, 알림1000개 한도 안에서 필터한다. 전체 삭제는 “삭제” 입력으로 구별한다. 표시 이름은 RAM 참고 정보이고 모든 쓰기 권한은 ID로 검사한다.

사용자 화면·마우스·키보드 자동 조작은 하지 않았다. 숨긴 Tk에서 DPI1.33/2.0·최소 창 크기·버튼과 목록 경계를 검사했으며 실제 사용자의 화면 조작/장시간 체감 UX는 별도 검증이 필요하다.

## 검증 결과와 한계

전체 회귀328개 통과(20.504초). 실제 SQLite 재시작/만료/격리/동시 요청·삭제 부활 방지/200개 예약 소진/손상 격리, 모의 Discord nonce·허용 멘션·범위·GPU 대기 독립성, 숨긴 Tk 검사를 포함한다. 테스트 수는 말투 품질 점수가 아니다.

실제 GPU 개발 평가: 각 모드24턴, 총72턴. 다른 사람의 옆 대화와 종료에서 침묵을 확인했지만 모든 중간 질문에 답하지는 않았다.

| 모드 | 실제 출력/24 | 사전 지정 사실 문자열 확인 | 의도한 침묵 외 누락 턴 |
|---|---:|---:|---|
| 기본 |20|5/6|15,16|
| 개인 말투 |21|6/6|13|
| 성인 유머 정책 |22|6/6|없음|

이는 합성 Discord transport+실제 GPU이며 사람의 자연스러움 평가가 아니다. 독립된 새 이름/호격/별칭/인용·다른 대상12사례는 세 모드 모두12/12 기대 행동과 일치했다. 작은 고정 사례의 성공을 실사용 정확도로 일반화하지 않는다.

장기 기억 GPU A/B: 재시작 후 기존 RAM 없이 본인 취향을 묻는 동일 질문에서 기억 없음0/3, 기억 있음3/3 사전 지정 사실을 포함했다. 응답 길이가 달라 소요 시간의 속도 우위로 사용하지 않는다. CPU 기억 조회100회 p50 1.7402ms/p95 2.0728ms였다.

후속 경로 GPU 비교는 워밍업1쌍 제외·교대 순서·각5쌍이었다. 기존 경로가 모두 침묵하고 새 경로는 응답해 동일 생성 작업이 아니었다. 따라서 다음 수치는 경로 관측값이며 성능 개선율이 아니다.

| 모드 | 기존 경로 p50/p95 초 | 후속 경로 p50/p95 초 | 응답 동일 쌍 |
|---|---|---|---:|
| 기본 |1.4322/1.4605|0.9569/0.9697|0/5|
| 개인 말투 |1.4330/1.4897|1.0908/1.1447|0/5|
| 성인 유머 정책 |1.4484/1.5003|1.0844/1.1064|0/5|

개발 실패도 보존했다. 초기 이름 진입을 “기존 대화 지속”으로만 판단해 첫 호출을 누락했고, 일반 시간 질문을 예약으로 오인했으며, 직접 이어지는 위로 요청에도 신규 끼어들기 민감성 veto를 적용했다. 각각 호출 기준·보수적 실행 의도 분류·신규 진입과 직접 응답 분리로 수정했다. 후속 holdout을 보고 하이퍼파라미터를 튜닝하지 않았다.

원본·상세 응답·타이밍·소스 스냅샷은 `local_data/companion-qa-20261019/`에만 있다. GPU4는 대화 개발 결과, release-probe는 새 이름과 경로 비교다. 이 GPU 결과는 뒤이은 알림 본문 편집 원자성 변경의 실제 Discord 검증을 대체하지 않는다. 새 가중치 선정·사람 블라인드 평가·다중 화자 장기 soak는 보류한다.

### 실제 Discord 예약 시험

사용자 허용을 받은 기존 테스트 채널에서 live-2를 실행했다. 소유자 실제 요청1건, 예약 확인1건, 요청자 멘션 알림1건을 실제 SDK 반환과 DB delivered로 확인했다. 실제 GPU 생성 작업이 실행 중인 시점에 예정 시각+1.936초(API1.312초) 전송됐으며 사용자가 한 번 정상 도착했다고 확인했다. 원래 HMAC 설정은 불변이었다. 시험 복사본만 사용했고 종료 시 Gateway/GPU 작업을 정리했다.

초기 live-1은 다른 채널에 요청해 수신0으로 종료했다. 재연결 뒤 허용 채널에서 성공했으며 다른 범위8이벤트는 시험 필터로 차단했다. 이 차단은 전체 생산 정책의 모든 상황 검증과 다르다. 전 모델의 장시간 실제 Discord 대화/Windows 직접 조작은 아직 미검증이다.

## 재현 명령

앱을 닫고 GPU 평가를 한 번에 하나만 실행한다. 실제 Discord 시험은 별도 사용자 허용이 있을 때만 실행한다.

```powershell
$env:PYTHONPATH='src'
.venv-gemma4/Scripts/python.exe -m unittest discover -s tests -q
.venv-gemma4/Scripts/python.exe -m compileall -q src/echomate_bot tools/verify_companion.py tools/verify_companion_release.py tools/verify_reminder_live.py
.venv-gemma4/Scripts/python.exe tools/verify_companion.py --output local_data/companion-new-run
.venv-gemma4/Scripts/python.exe tools/verify_companion_release.py --output local_data/companion-independent-run
```

GPU 스크립트는 출력 폴더가 이미 있으면 덮어쓰지 않는다. 실제 Discord QA 도구는 원래 설정을 읽기만 하고 별도 QA 복사본을 사용한다. 기능 구현/모의 이벤트/실제 GPU/실제 Discord/사용자 화면 관찰을 서로 구별해 기록한다.


보존 최종 검사: 기존1104파일 누락0. 가중치/학습자료/원래 서명 설정은 보존했다. 실제 QA 과정에서 기존 runtime.lock, diagnostic.jsonl, sent.sqlite3, telemetry.json 네 운영 파일은 실행 기록이 갱신됐다. 원래 파일을 삭제/되돌리지 않았다. QA 설정 폴더를 써도 EchoClient의 기본 ledger 경로가 운영 폴더를 가리키던 원인을 확인해, visual/ledger/진단을 설정 폴더에 함께 두도록 수정하고 경로 회귀 검사를 추가했다. 이 최종 경로 격리 수정은 모의 SDK/전체 회귀 검증이며 실제 Discord 재시험은 하지 않았다.
