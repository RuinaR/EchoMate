## 재현한 코드 결함과 수정

### 이름만으로 등록 성공을 판단한 경로

이전 `apply_commands`는 전역 sync → 모든 서버별 삭제/sync → 마지막 재조회 순서였다. 전역 등록 결과가 빈 목록인 모의 실패를 주입하면, 전역 실패를 확인하기 전에 서버별 삭제를 시작할 수 있었다. 이는 재현한 **부분 실패 위험**이며 실제 사용자 서버에서 이 순서로 사라졌다는 증거는 아니다.

새 경로는 실제 SDK가 생성할 전역 payload를 먼저 검증하고, 전역 `/동의`를 재조회해 이름·slash type·서버 문맥/서버 설치·기본 권한·NSFW 계약을 확인한 뒤에만 서버별 정리를 시작한다. 마지막 전체 재조회도 유지한다. 로컬 명령은 `contexts:[0]`, `integration_types:[0]`, default_member_permissions:null을 명시하며 기존 서버 전용 `/동의` 정책을 따른다. 실제 API가 아직 이 payload를 받았다는 뜻은 아니다.

검토 fingerprint에 접근 설정을 포함해 이름과 ID가 같아도 권한/문맥/설치 범위가 바뀌면 재승인을 요구한다. 다른 Application이나 다른 서버 범위의 응답을 거부한다. 실패/취소는 단계·예외 종류·HTTP 상태/Discord 오류 코드만 비공개 감사에 기록하고 원문 예외/토큰은 기록하지 않는다. 부분 실패 후 pending은 유지하고 이전 승인 객체를 폐기한다. 시작 시 pending을 자동 실행하지 않는다. 조회와 변경은 같은 lock으로 직렬화한다.

서버별 정리와 전역 등록 전체를 하나의 Discord 트랜잭션으로 만들 수는 없다. 후속 서버 접근 실패는 부분 완료로 남으며, 외부 관리자가 재조회 직후 원격 명령을 변경하는 경쟁까지 제거했다고 주장하지 않는다. 자동 rollback/반복 삭제 대신 최신 목록 검토와 새 승인을 요구한다.

### SDK 2.7.1의 zero-based 범위 배열 해석

실제 설치된 SDK로 `AppCommand`를 만들었을 때 원본 API 배열 `[0]`이 `allowed_contexts.to_array()`/`allowed_installs.to_array()`에서 `[]`가 됐다. [공식 2.7.1 모델 코드](https://github.com/Rapptz/discord.py/blob/v2.7.1/discord/app_commands/models.py)는 해당 필드를 flags로 변환하고, [공식 flags 코드](https://github.com/Rapptz/discord.py/blob/v2.7.1/discord/flags.py)의 ArrayFlags 변환은1-based 배열 이동을 적용한다. 이것은 이번 확장된 접근 범위 검사의 오판 원인이며, 과거 이름만 보던 코드에서 실제 비표시를 만들었다는 증거는 아니다.

설치 라이브러리나 전역 SDK를 monkeypatch하지 않았다. `_fetch_command_rows`는 기존 SDK HTTP의 전역/서버별 GET에서 받은 JSON 배열을 `command_contract.rows`로 검증해 보존한다. 요청을 두 번 보내지 않고 CommandTree의 송신 직렬화/sync는 그대로 사용한다. missing/null, 빈 배열, 서버0, DM1, 사용자 설치1을 구분한다. 서버별 권한 덮어쓰기와 실제 Discord 사용자 화면의 접근성은 여전히 이 metadata만으로 확정할 수 없다.

### UI·진단

응답 방식 화면의 혼합 버튼을 **명령 목록 조회**와 **변경안 검토·승인**으로 나눴다. 승인 버튼은 유효한 검토 객체가 있을 때만 활성화한다. 조회 실패/연결 변경은 오래된 UI 검토를 폐기하고403/404를 안전한 한국어로 안내한다. 승인 팝업은 Application·전역/서버별 전후 목록과 범위/기본 권한 정보를 보여주며 기존 확인 문구를 유지한다. 성공 메시지는 **API 등록 확인**과 **클라이언트 표시/실행 미확인**을 분리한다. 진단 내보내기에는 안전한 명령 단계/오류 코드만 추가했다. 다른 UI/로더/큐/저장소는 재설계하지 않았다.

## 모델 선택과 보존

기존 분할 폴더의 구조·677개 텐서 헤더/인덱스 범위·크기23,919,548,248bytes·최대 shard2GiB 미만·검증 프로필을 다시 확인하고 GPU 로딩/추론했다. 전체23GB 텐서별 checksum을 다시 계산한 검사는 아니다. 원본과 가중치/LoRA를 쓰거나 이동하지 않았다. 운영 `base`는 그대로고 GPU fixture에서만 분할 경로를 지정했다. 실제 운영 적용은 별도 사용자 승인 대상이다. 모델 전환 실패/이전 선택 복구/캐릭터 보존/재시작은 기존 임시 설정·모의 로더 회귀로 확인하며 이번에 반복 GPU 전환을 했다고 하지 않는다. 추가 메모리 최적화는 하지 않았다.

## 실제 조회·복구를 재개하는 순서

1. 사용자가 실행한 설치/버전/서버와 비공개 감사 존재 여부를 확인한다. 현재는 당시 감사가 없고 App ID도 미확정이다. 토큰을 채팅에 받지 않는다.
2. **새 읽기 전용 승인 후에만** 현재 Bot 보관 형식을 확인해 메모리에서 인증하고 GET `/users/@me`, `/oauth2/applications/@me`로 Bot/Application 대응을 식별한다. 같은 Application의 GET `/applications/{id}/commands`, 로컬 설정 대상 서버의 GET `/applications/{id}/guilds/{guild}/commands`만 수행한다. 결과는 비공개 `local_data/command-recovery-20261024/remote-readonly.json` 같은 별도 파일에 허용 필드만 저장한다. Gateway·닉네임 적용·GPU·스케줄러·메시지 송신은 필요 없다. 기존 앱의 일반 봇 시작은 부수효과가 있으므로 이 독립 조회 대신 자동 실행하지 않는다. 현재 그런 인증 조회는 실행하지 않았다.
3. API 목록·접근 metadata·Application 설치·서버별 명령 권한/클라이언트 표시를 대조해 원인을 좁힌다. 승인된 명령 목록 조회만으로 채널 권한/개인별 overrides까지 조회한 것으로 간주하지 않는다.
4. 대상과 전후 목록/부분 실패 영향을 제시해 **별도 변경 승인**을 받는다. 변경 후 전역과 서버별 API 재조회, 사용자 Discord 화면 표시, 실제 `/동의` 본인 패널, 기존 동의/관계/기억 보존을 각각 확인해야 복구 완료다. 다른 앱/봇은 대상이 아니다.

남은 차단은 실제 명령 접근 복구, 넓은 사회적 의미 오개입/후속 누락/대화 연결, 실제 친구 서버/사용자 UI, 다른 Windows·장시간 실사용이다. 이번 소스는 사용자 승인 없이 원격 명령이나 운영 모델을 바꾸지 않는다.
